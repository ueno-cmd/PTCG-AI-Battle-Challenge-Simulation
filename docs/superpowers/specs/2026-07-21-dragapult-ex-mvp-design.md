# ドラパルトexデッキ MVP開発 設計書

## 背景・目的

現在のメイン提出はルカリオex（`src/lucario_agent/`）。2つ目の提出枠として、以前ブレスト中断していた「ドラパルトex」デッキの新規開発を2026-07-21に再開することが決定した（[[project_ptcg_backlog]]参照、2026-07-17のブレスト中断分`docs/analyses/20260717-dragapult-deck-strategy-summary.md`とは別の再検討）。

再開にあたり、着手前の調査として「実戦で遭遇したドラパルトex使用者になぜ実力差があるのか」を実バトルログから調査した。要点：

- `data/battle_logs/`全310件中、相手デッキにドラパルトex(ID121)を含む対戦は34件（Kagura_UT視点で13勝21敗）
- そのうち12件（35%）はKaggle公式サンプルエージェント（`notebooks/samples/a-sample-rule-based-agent-dragapult-ex-deck.ipynb`）と完全に同一の60枚構成だった。人間のジムバトル優勝リスト（`docs/analyses/20260717-...md`）と完全一致する相手は実戦に0件
- デッキ構成の一致・不一致は勝敗とほぼ無相関（サンプル一致組の勝率33% vs それ以外41%）
- 強い相関が見られたのは実行力：Kagura敗北21件中20件（95%）は相手がファントムダイブ（メイン技、`attackId=154`）を実際に発動できていた。Kagura勝利13件中9件（69%）は相手がファントムダイブを一度も撃てず、うち6件はドラパルトexへの進化自体が成立していなかった
- サンプルのコードを詳読した結果、進化ルートは「ふしぎなアメ経由」「ドロンチ経由の通常進化」の両方が実装済みで、単線化はしていない（当初の見立てを訂正）。「進化失敗」は主に手札運による可能性が高く、現時点でロジック上の欠陥と断定する根拠はない
- 一方、ボスの指令（Boss_Orders, ID1182, ×3採用）の使用条件は`if plan_a.attack > 0: score = 60000`のみで、「今のベスト攻撃プランがベンチの相手を狙っている時」しか使わない。ベンチの弱い駒を先出しで引きずり出すような探索的な使い方はしていない

ユーザー方針：**「実行力の高いAIを作る」ことを軸に、「最小構成でまず提出して実戦データを集める」進め方（MVPファースト）で検証する**。仮説（ボスの指令の使用改善が勝率に効くか等）は実装して終わりではなく、提出後の実ログで検証してから次の手を判断する。

## スコープ

### 今回やること

1. `src/dragapult_agent/main.py`：Kaggle公式サンプル（`notebooks/samples/a-sample-rule-based-agent-dragapult-ex-deck.ipynb`のcell3、855行）のロジックを移植する
2. `src/dragapult_agent/constants.py`：カードID定数を切り出す（他デッキとの最小限の一貫性のため。`combat.py`のようなロジック分離はしない）
3. ボスの指令のスコアリングに、確定的な引き剥がし先が無い場合でも一定確率で探索的に先出しする分岐を追加する（`src/lucario_agent/main.py`の`BossOrdersPolicy`、323〜332行目で実証済みのパターンを移植）
4. デッキ60枚をKaggle公式サンプルと同一構成でセットする（下記「デッキ構成」参照）
5. ACE SPEC制限（アンフェアスタンプ、1枚制限）を含む単体テストを追加する
6. `decks/dragapult_20260721.py`（他デッキの`decks/*.py`と同じ命名慣習）としてデッキ定義を用意する

### 今回やらないこと

- 進化ルートの改修：サンプルは既に「アメ経由」「通常進化」の両方をフォールバックとして持っており、現時点でロジック上の欠陥と断定できる根拠がない。**提出後の自分のログで実際に進化遅延が発生したら、その時点で原因（手札運かロジックか）を切り分けてから判断する**
- アンフェアスタンプ（ACE SPEC、1080）の使いどころの精緻化：サンプルの挙動（確定KO時80000点、それ以外は温存80点）をそのまま踏襲する。「相手の手札を減らせる」という副次的なメリットの評価は今回スコープ外（ユーザー確認済み）
- ジムバトル優勝リスト（`docs/analyses/20260717-...md`）への構成変更：実戦で遭遇した相手と一致しないため、今回はKaggle公式サンプルの構成を採用し、AIロジックの改善効果を同一デッキで検証できるようにする
- `combat.py`分離やテーブル駆動アタッカー選択など、ルカリオex同等の構造化（YAGNI。MVP到達を優先し、実測結果を見てから構造化を検討する）
- ボスの指令以外のトレーナーズカード（クラッシュハンマー・タケシのスカウト等）のスコアリング見直し（今回の調査で明確な問題は確認していない）

## 設計1：ボスの指令の探索的先出し

### 対象コード（`src/dragapult_agent/main.py`、サンプル移植後の`hand_score`関数内）

現状（サンプル）：

```python
elif id == Boss_Orders:
    if plan_a.attack > 0:
        score = 60000
```

`plan_a.attack`は`main_option_proc`（190〜286行目相当）が計算する「現在のベスト攻撃プラン」が指すターゲットのインデックス（0=アクティブ、1以上=ベンチ）。`plan_a.attack > 0`は「ベストプランがベンチの相手を狙っている」ことを意味し、この条件が満たされた時だけボスの指令が高スコアになる。裏を返すと、確定的に強い引き剥がし先が"まだ"見えていないターンではボスの指令のスコアは常に0で、使われない。

修正後：

```python
BOSS_ORDERS_EXPLORE_EPSILON = 0.28  # ルカリオexのEPSILONと同値（src/lucario_agent/combat.py:13）を初期値として踏襲
_dragapult_rng = random.Random()

...

elif id == Boss_Orders:
    if plan_a.attack > 0:
        score = 60000  # ベストプランがベンチ狙いを示している：即使用
    elif _dragapult_rng.random() < BOSS_ORDERS_EXPLORE_EPSILON:
        score = 30000  # 確定的な引き剥がし先がなくても、一定確率で探索的に先出しする
```

`src/lucario_agent/main.py`の`BossOrdersPolicy`（確定KO時8800点／epsilon確率で探索的先出し6000点／それ以外温存-1点）と同じ3段階の考え方を、サンプルの手続き型コードにそのまま適用する。ルカリオ側は`_rng`（モジュールグローバルの`random.Random`インスタンス）と`EPSILON=0.28`定数を使っており、`dragapult_agent`側にも同様の`_dragapult_rng`・`BOSS_ORDERS_EXPLORE_EPSILON=0.28`を新設し初期値として踏襲する（提出後の実測次第でチューニング対象になり得るが、初回提出時点では変更しない）。探索時のスコア30000は、他の高優先度カード（Dragapult_exの進化40000等）より低く、通常攻撃の温存カード（Boss_Orders確定KO時60000）より低い中間的な値として設定する。サンプルは`random`モジュールを未使用のため、`src/dragapult_agent/main.py`冒頭に`import random`を追加する。

### データフロー

`hand_score`の戻り値は`agent()`内でカードプレイ候補のスコアとして使われる既存の仕組みをそのまま使う。変更が影響するのはボスの指令のスコアリング時のみで、他のカードのスコアリングロジックへの影響はない。

### エラーハンドリング

既存のサンプルコードの例外処理方針をそのまま踏襲する（未知のIDが来ることは想定しない、既存パターンと同様）。

## テスト方針（TDD）

1. **デッキ構成テスト**（`tests/test_dragapult_deck.py`、既存の`test_lucario_deck.py`等と同じパターン）：60枚合計の検証、ACE SPEC（`ACE_SPEC_IDS = {1080}`）が1枚のみであることの機械的チェック
2. **ボスの指令スコアリングの単体テスト**（`tests/test_dragapult_agent.py`）：
   - `plan_a.attack > 0`（確定的な引き剥がし先あり）のとき60000を返す
   - `plan_a.attack <= 0`だが探索的先出しの乱数条件を満たすとき30000を返す
   - どちらの条件も満たさないとき0（温存）を返す
3. **既存テストの回帰確認**：`uv run pytest -q`でリポジトリ全体が全件PASSを維持することを確認する

## 検証計画（提出後）

1. Kaggleへ提出し、新規バトルログを取得する
2. `data/competition/EN_Card_Data.csv`ベースのログ解析（[[project_battle_log_parser]]の手法）で以下を確認する
   - ボスの指令の使用回数が、実測した「サンプル一致組」（0〜1回/試合が大半）より増えているか
   - 自分側のドラパルトexへの進化タイミング・ファントムダイブの初発動ターン・勝率
   - 進化が遅延したケースが発生した場合、手札運かロジックかをログから切り分ける
3. [[project_ptcg_backlog]]のログ蓄積ペース（提出直後は数十分で20戦程度たまるが、そこを超えると1週間程度かかる傾向）を踏まえ、初動20戦程度で「壊れていないか」を確認し、統計的な勝率評価は複数回の提出を重ねてから行う

## 構造面の確認（YAGNI判断）

今回touchするのは`hand_score`内のボスの指令の分岐のみで、既存の`main_option_proc`（ベンチ分散ダメージの組み合わせ探索）や進化ルートのロジックには手を入れない。`combat.py`分離・テーブル駆動アタッカー選択などの構造化は、MVP提出・実測結果を見てから改めて検討する（ユーザー承認済みの方針）。
