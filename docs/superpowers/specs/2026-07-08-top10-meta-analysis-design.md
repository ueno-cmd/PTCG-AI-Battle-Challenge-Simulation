# TOP10メタ分析ツール 設計書

**作成日：** 2026-07-08
**背景：** 現在自作最高成績のナンジャモデッキ（ビリリダマ低耐久）、代替候補のタケルライコ＝ジャモライコ構成（ハンドリング難）、環境上位のフーディン・ドラパルトex、ルカリオexの勝率は良いがLBポイント効率が低いという複数の課題を前に、個別に対処するのではなく「今のLB TOP10が実際に何をしているか」を先にデータで把握してから、強化学習（RL）導入も含めた今後の方針（デッキ設計・RL対象選定）を決めることになった。

前回セッション（2026-07-08前半）で提示していたRL導入のサブプロジェクト分解案（①デッキ設計→②RL環境設計→③モデル・学習パイプライン→④評価・提出）は未承認のまま中断していたが、本設計はその**前段（サブプロジェクト0）**として、①のデッキ設計判断とRL設計の入力材料を作るものである。

---

## ゴール

1. 現行LB TOP10プレイヤーの直近バトルログ（各3件、計30件、ユーザーが手動DL）から、対戦相手側のデータのみを対象に以下2点を分析するツールを作る
   - **デッキ分布**：実際に環境で使われているデッキ構成（フーディン・ドラパルト以外の型も含む）
   - **意思決定パターン**：アタッカーの技選択・エネルギー配分・入れ替えタイミングなど、RL設計（状態表現・行動空間・報酬設計）のヒントになる情報
2. 分析結果は1つのMarkdownレポートに集約し、次回セッションでのRLスコープ決定（対象デッキ選定、サブプロジェクト①）の判断材料とする
3. 再利用可能なツールとして作る（LBの変化に合わせて今後も同じ手順で再実行できる）

## 調査で判明した重要な制約：「点効率」は対象外

Web検索（2クエリで独立に一致）により、本コンペ（Simulationカテゴリ）は**Gaussianスキルレーティング方式**（TrueSkill系）であり、
- 勝敗のみがレーティング変動に影響し、**勝ち方（マージン・ターン数・KO数）はレーティングに影響しない**
- 対戦相手は自分と近いレーティング帯からマッチメイキングされる
- 最終順位には**直近2件の提出**のみが反映される

ことが分かった（Kaggle公式ルールページ自体はJS描画のためWebFetchでは直接引用できず、検索結果の要約による。断定はできないためユーザー側での一次情報確認が望ましい）。

バトルログの`rewards`フィールドは`[1, -1]`のような勝敗のみで、対戦相手のレーティングや点数の増減はログJSONのどこにも含まれていない。したがって「ルカリオが勝っているのにポイントが伸びない」という現象は**レーティングメカニクスの問題であり、バトルログの中身をいくら分析しても解決しない**と判断し、当初想定していた「勝ち方とポイント効率の相関」分析は**今回のスコープから完全に除外する**。

## 入力データの契約

- ユーザーが手動DLしたJSON30件は、既存の`data/battle_logs/`にそのまま配置する（新規フォルダは作らない）
- 対象ログのリストを`data/top10_meta_targets.csv`としてユーザーが作成する。フォーマットはCSV形式（ヘッダなし、`#`始まりの行はコメントとして無視）：
  ```
  # 形式: episode_id,target_player_name
  # target_player_name は info.Agents の名前と完全一致させ、そのログ内で分析対象とする側（TOP10プレイヤー側）を明示する
  84580427,Zammaar Shafqat Malhi
  83433347,Canon
  81826988,keidroid
  ```
  - `target_player_name`を1行ごとに明示する理由：TOP10プレイヤー同士の対戦ログ（自分＝Kagura_UTが関与しない試合）も対象になり得るため、「相手側＝分析対象」という単純な決め打ちができない。`gold.py`は`info.Agents`の中から`target_player_name`と完全一致する側（`player0`/`player1`のどちらか）を機械的に特定するだけでよく、TOP10プレイヤー名リストとの突合ロジックを別途持つ必要がなくなる
  - 対象選定・ファイル作成自体はユーザーの手作業（ログJSON内に「LB順位」の情報が無いため自動化できない）

## アーキテクチャ

ハイブリッド方式を採用する。ただし実装調査の結果、既存の`silver.py`が実際に出力しているのは**勝者名・ターン数（`total_steps`）のみ**であり、デッキリストやRESULT理由は含まれていないことが分かった（`bronze.py`は生JSONの単純コピー）。そのため「デッキ分布・基本サマリー」のうち実際にsilverを再利用できるのは勝敗・ターン数だけで、**デッキリスト抽出とアーキタイプ分類は意思決定パターン抽出と同じく生JSON直読みの新規実装**になる。両者とも生JSONを扱う点は共通なので、`gold.py`に両方の関数を置く。

```
data/top10_meta_targets.csv          … 対象30件の episode_id,target_player_name リスト（ユーザー作成）
data/battle_logs/<id>.json            … 既存の生ログ（そのまま）

src/etl/silver.py                     … 【修正】rewardsにNoneが含まれる場合にクラッシュしないようガード追加（勝者名・ターン数の取得に利用）
src/etl/gold.py                       … 【新規】(a) 意思決定パターン抽出 (b) デッキリスト抽出・アーキタイプ分類。いずれも生JSON + LogType/SelectContext直読み
scripts/analyze_top10_meta.py         … 【新規】集約CLI

output/top10_meta_report_<実行日>.md  … 生成されるレポート
```

`scripts/analyze_top10_meta.py`は`data/top10_meta_targets.csv`を読み、対象ログそれぞれについて (a) `silver.py`で勝者名・ターン数を取得、(b) `gold.py`でデッキリスト・意思決定イベントを抽出し、1つのMarkdownレポートに集約する。既存の`scripts/etl_battle_log.py`と同じCLIパターン（`uv run python scripts/xxx.py`）を踏襲する。

`silver.py`のNone-reward修正は既知のバグ（`parse_to_silver()`が`rewards`の片方が`None`の試合でクラッシュ、2026-07-03にログ83510250で発生確認済み、[[project_battle_log_parser]]参照）の解消であり、既存の全デッキ分析にも波及する副次的な改善になる。

`gold.py`は今回新規のレイヤーだが、意思決定パターン抽出という性質上、将来の別調査（例：Crustle対策の実戦検証など）にも再利用できる汎用モジュールとして設計する。

## コンポーネント詳細

### `src/etl/silver.py`（修正）

`parse_to_silver()`内の勝敗判定を、`rewards`に`None`が含まれる場合は`None`を最小値として扱うようガードする。

### `src/etl/gold.py`（新規）

生JSONの`steps[i][player]['observation']['logs']`を`LogType`（`data/cg/api.py`）でデコードし、`target_player_name`と`info.Agents`が一致する側の行動のみを対象に、以下を1試合分のイベント列として抽出する関数群を提供する。

- `ATTACK`イベント：使用した技・その時点のエネルギー数・与えたダメージ
- `select.context`が`SWITCH`/`TO_ACTIVE`系のイベント：交代先ポケモン・その時点のHP
- サポート（トレーナーズ）カード使用イベント：カードID・使用ターン数
- `RESULT`イベント：決着理由（プライズ0／デッキアウト／バトル場0／カード効果）

`serial`（カード1枚を一意に指す識別子、[[project_battle_log_parser]]参照）を使い、同名カードでも枚数を正確にトラッキングする。

### デッキ分布（`src/etl/gold.py`内、新規実装）

`steps[0][0]['visualize'][0]['action']`（開幕時点で両者の60枚デッキ全カードIDが入っている）から対戦相手側の60枚を取得し、`EN_Card_Data.csv`でID→名前変換する。ex／主要アタッカーの出現有無でアーキタイプを分類する簡易ロジックとする（既存の目視分類の考え方をコード化するのみで、厳密な分類器は作らない）。

### 集約レポート（`scripts/analyze_top10_meta.py`）

30件を横断し、以下をMarkdownにまとめる。

- デッキ分布表（アーキタイプ別出現回数・使用プレイヤー名）
- 意思決定パターンの記述統計（アタッカー別「技を打った時点の平均エネルギー数」、代表的なサポートカードの平均使用ターンなど）
- 個別試合の生ログへのリンク（ファイル名）を残し、後で深掘りできるようにする

## テスト方針（TDD）

- `src/etl/silver.py`：`rewards=[1, None]`のようなfixtureで回帰テストを追加（実ログ`83510250.json`が既知の再現ケース）
- `src/etl/gold.py`：`data/battle_logs/`内の既存ログ数件をfixtureとして使い、ATTACK/SWITCH/RESULTイベントが正しい件数・内容で抽出できることをユニットテストで検証
- `scripts/analyze_top10_meta.py`：対象30件が揃う前でも、既存ログ数件を`top10_meta_targets.csv`に入れてエンドツーエンドで実行し、レポートが生成されることを確認

## スコープ外・既知の制約

- 「勝ち方とポイント効率」の分析は対象外（前述の通りレーティングメカニクスの問題でありログからは検証不能と判明したため）
- 「TOP10」の選定・30件のダウンロードはユーザー側の手作業（自動化しない）
- デッキアーキタイプの自動分類は簡易ロジック（主要ex／キーカードの有無ベース）であり、厳密な分類はレポートを見た人間が最終判断する前提
- 本設計・実装はRLサブプロジェクト0（環境メタ分析）のみを対象とし、RL自体の状態表現・行動空間・報酬設計（サブプロジェクト②）や、デッキ設計そのものの変更判断（サブプロジェクト①）には踏み込まない。分析結果を踏まえたRLスコープ決定は次回セッションで改めて行う
