# グリムスナールex ハイブリッドチューニング設計書（ルールベース方策 × 進化探索）

作成日: 2026-07-12
ステータス: ユーザーレビュー待ち

## 1. 背景と目的

### 背景
- ルールベースエージェントはLBスコア700点台で頭打ち（最高735.8）
- 2026-07-11のevo_search RL実験は、学習が成立しないまま（世代ベスト報酬 4→2→4→2）
  弱い方策を提出してしまい、LBが600→450に下落した
- 原因分析の結果、evo_searchの方策（17個の汎用重み）は盤面の状況を見ておらず、
  **手書きのルールベース（`src/grimmsnarl_agent/main.py`）の方が方策として賢い**と判明

### 目的（ハイブリッド案）
ルールベースの頭脳（場合分けの判断ロジック）はそのまま使い、その中に人間の勘で
決めてある**数字だけをRLの仕組み（進化探索＝変異→自己対戦→選抜）で自動調整**する。
狙いは「人間には決めきれない細かい数字の境界」を機械に磨かせて700点の壁を破ること。

### 今回のスコープで検証する仮説
2026-07-05にユーザーが立てた仮説「グリムスナールex・キチキギスex・モルペコの誰に
エネルギーを寄せるかのスコアが僅差で競り合っており、配分が分散して挙動が不安定になる」。
エネルギー配分の数字をチューニング対象にすることで、この仮説の検証を兼ねる。

## 2. 全体の進め方（2段階）

```
ステップ0: 校正実験（このspecの前半）
  「強い設定と弱い設定を何試合戦わせれば、強い方がちゃんと勝ち越すか」を実測する。
  2026-07-11の失敗原因（4試合評価がノイズに支配された）の再発防止。

ステップ1: 本番チューニング（このspecの後半）
  ステップ0で決めた試合数を使い、エネルギー配分の数字8個だけを進化探索で調整する。
  「学習曲線が右肩上がりになるか」「手書きの数字を超えられるか」を確認する。
```

ステップ0の実装（数字の辞書化＋自己対戦ループ）はステップ1でそのまま再利用する。
使い捨ての実験ではなく、ハイブリッドの土台工事を兼ねる。

## 3. コード変更：チューニング対象の数字を辞書に集約する

### 対象ファイル
`src/grimmsnarl_agent/main.py`（既存。挙動は一切変えない）

### 変更内容
`_score_attach` に直接書かれているエネルギー配分の数字8個を、モジュール直下の
辞書 `TUNABLE_WEIGHTS` に集約する。デフォルト値＝現在の手書き値。

```python
# エネルギー配分のチューニング対象（進化探索で調整する数字）
# デフォルト値は手書きの現行値。ノートブック側からこの辞書を差し替えて学習する
TUNABLE_WEIGHTS = {
    "grimmsnarl_base":          9000,  # オーロンゲ2エネ未満の基礎点
    "grimmsnarl_slope":         1000,  # 同・エネ1枚ごとの減点
    "grimmsnarl_surplus_base":  3500,  # オーロンゲ2エネ確保後の基礎点
    "grimmsnarl_surplus_slope":  100,  # 同・エネ1枚ごとの減点
    "fezandipiti_base":         5000,  # キチキギスの基礎点
    "fezandipiti_slope":         500,  # 同・エネ1枚ごとの減点
    "morpeko_base":             4500,  # モルペコの基礎点
    "morpeko_slope":             200,  # 同・エネ1枚ごとの減点
}
```

### 変えないもの（構造は人間の設計のまま固定）
- 場合分けの構造そのもの（「オーロンゲ2エネ確保後にキチキギス・モルペコが浮上する」
  というゲート条件、閾値の2エネ・3エネ）
- エネルギー以外のスコア（PLAY優先度・攻撃選択・交代先選択など全て）
- デッキ（`decks/grimmsnarl_20260701.py`、60枚構成）

### 品質担保
既存テスト88件（`tests/test_grimmsnarl_agent.py`）が全てPASSすること＝辞書化しても
挙動が変わっていないことの証明。加えて「辞書の値を差し替えるとスコアが変わる」ことを
確認するテストを最低1件追加する。

## 4. ステップ0：校正実験ノートブック

### ファイル
`src/rl_experiments/grimmsnarl_calibration_experiment.ipynb`（新規。命名規則
`{デッキ名}_{手法タグ}_experiment.ipynb` に従う。gitignore対象なのでコミットなし）

### やること
main.pyのエージェント（辞書化済み）を2つの設定で自己対戦させ、勝敗を数える。

- **設定A（強いはず）**: `TUNABLE_WEIGHTS` のデフォルト値（手書きの現行値）
- **設定B（弱いはず）**: エネルギー配分の優先順位をわざと壊した値。
  具体的には `grimmsnarl_base` と `morpeko_base` を入れ替える
  （＝オーロンゲが攻撃準備できる前にモルペコへエネルギーを注ぎ込む、明らかに悪い方針）

### 測定内容
1. **A vs B を200試合**：累積勝率の推移を10試合刻みで記録。
   「何試合の時点で、Aの勝ち越しが安定して見えるようになるか」を観察する
2. **A vs A（ミラー）を200試合**：ノイズの基準線。理論上は勝率50%に収束するはず。
   これが大きく偏るなら先手後手の有利など別の偏りがあると分かる
3. 実行時間を記録する（前回実績：148試合で約8.4秒 → 400試合でも1分以内の見込み。
   これが大きく外れる場合はステップ1の計画に反映する）

### 判断基準（ステップ1へ進む条件）
- A vs B で、ある試合数N以降Aの勝率が一貫して60%を超える → そのNを
  ステップ1の `GAMES_PER_CANDIDATE`（1候補あたりの評価試合数）に採用する
- 200試合してもAとBの差が見えない場合 → 「壊した設定でも勝敗に影響しない」＝
  エネルギー配分は勝敗を左右していない、ということなので、チューニング対象の
  選定からやり直す（ステップ1には進まない）

### デッキの読み込み
既存のevo_search実験ノートブックと同じglobパターンで、アップロード済みKaggle
データセットから読み込む：
`glob.glob('/kaggle/input/datasets/**/deck_20260705_185905.csv', recursive=True)[0]`

### 実行
Kaggle上でユーザーが実行する（macOSでは`libcg.so`が動かないため）。
注意：`libcg.so`はseedを受け取れないため結果は毎回変わる。校正実験は「傾向」を
見るものであり、厳密な再現性は求めない。

## 5. ステップ1：本番チューニングノートブック

※詳細設計はステップ0の結果を見てから確定する。ここでは方針のみ固定する。

### ファイル
`src/rl_experiments/grimmsnarl_hybrid_evo_experiment.ipynb`（新規）

### 学習の仕組み（前回evo_searchと同じループ＋失敗原因の対策入り）
- 変異→自己対戦評価→選抜の進化探索。ただし：
  1. **評価試合数**: ステップ0で実測したNを使う（前回の4試合は少なすぎた）
  2. **変異にクリップを入れる**: 各数字はデフォルト値の0.25倍〜4倍の範囲に制限
     （前回は無制限で、重みがマイナスに転落して崩壊した）
  3. **評価相手はデフォルト値の方策に固定**: 挑戦者（変異した数字）vs 王者
     （手書きの数字）で勝率を測る。「手書きを超えたか」が常に直接測れる
- チューニング対象は `TUNABLE_WEIGHTS` の8個のみ
- 世代数・集団サイズはステップ0で測った実行時間から逆算して決める
  （Kaggleセッション内で30分以内を目安とする）

### 成功の判定
- 学習曲線（世代ごとのベスト勝率）が右肩上がりになること（前回は 4→2→4→2 だった）
- 最終的な数字がデフォルト値に対して勝率55%以上なら「手書き超え」とみなし、
  提出用の重みとして採用を検討する
- 挙動の質は提出前に必ずバトルログで確認する（「攻撃回数ゼロ」のような
  崩壊が起きていないか）。前回の轍を踏まず、LB提出は確認後にユーザーが判断する

### 提出パッケージング
前回evo_search実験ノートブックの `main.py` 書き出し→`submission.tar.gz` 生成の
仕組みを流用する。ただし書き出す方策は今回のルールベース版main.py＋学習後の
`TUNABLE_WEIGHTS`。

## 6. スコープ外（やらないこと）

- エネルギー配分以外の数字のチューニング（グループB〜E。ステップ1成功後に検討）
- ルカリオexデッキへの横展開（型が確立してから）
- 場合分け構造（ゲート条件・閾値）自体の学習
- ニューラルネット・MCTS等の表現力の高いRL
- デッキ構成の変更・デッキ構築支援モデル（card2vec等）の導入

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 校正実験でAとBの差が出ない | エネ配分が勝敗に効いていない証拠として持ち帰り、対象を再選定（無駄な学習を回す前に分かるのがステップ0の価値） |
| ミラー自己対戦への過適合（実LBの多様な相手に弱い） | 今回は割り切って許容。学習後の重みはLB提出前にバトルログで挙動確認 |
| seedが効かず結果が毎回変わる | 校正は傾向のみ判断。本番は評価試合数を十分に取ることでノイズを均す |
| Kaggle実行時間の超過 | ステップ0で実測した1試合あたりの時間から世代数・集団サイズを逆算 |
