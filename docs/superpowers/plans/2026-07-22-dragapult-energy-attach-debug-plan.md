### 今回のデバッグ対象：`attach_score()`のベンチ配分ロジック

65回のベンチ向けエネルギー装着のうち、アクティブがまだ本命技（ファントムダイブ、2エネ必要）を撃てる状態でなかったケースが44件あった。内訳の当初分類：
- 25件：アクティブがスボミー/フェザンディピティex/ラティアスex/ニャースexだった → 専用ロジック（`attach_score`内でこれらの種族は`return -1`となる別分岐）で説明可能、と当初判定
- 19件：アクティブがドラメシヤ/ドロンチ/ドラパルトexで、汎用ロジックの範囲 → `attach_score()`を忠実に再現して手動でスコア計算した結果、15件は「ベンチが実際に上回っており設計通り」、**4件は「アクティブの方が高スコアなのにベンチへ配分された」という矛盾**として残った

### この4件のうち1件を深掘りしたところ、分析手法自体に致命的なバグが2つ見つかった

**バグ①：1つの観測ステップ（`data["steps"][i]`）に複数ターン分のログイベントが混在しうる。**
このゲームのログ仕様では、あるプレイヤーの`status=='ACTIVE'`なステップでのみ新規イベントが記録され、`INACTIVE`の間は直前のスナップショットが複製される（[[project_battle_log_parser]]参照）。そのため、1回の観測ステップの中に「相手のターン終了→自分のターン開始→複数アクション→自分のターン終了→相手のターン開始」のような、**複数ターンにまたがる大量のイベントが1つのステップにまとめて記録されることがある**。ステップ単位で「前のターンの状態」を判定すると、実際には同じステップ内の別ターンの状態を参照してしまう。

（この同じ原因で、前回アンフェアスタンプの`pre_ko`判定でも一度誤診断している。デバッグ手法として「ステップ境界」を信頼してはいけないという教訓は[[feedback_verify_analysis_claims]]に記録済み。）

**バグ②：`LogType.SWITCH`（type=8）のフィールド名が意味と逆。**
`data/competition/sample_submission/cg/api.py`のコメントを正確に読むと：
```python
# cardIdActive (int): Moving to the Bench Pokémon ID       <- アクティブ「から」ベンチへ移動する方
# serialActive (int): Moving to the Bench Pokémon serial
# cardIdBench (int): Moving to the Active Pokémon ID        <- ベンチ「から」アクティブへ移動する方
# serialBench (int): Moving to the Active Pokémon serial
SWITCH = 8,
```
つまり `cardIdActive`/`serialActive` は「**アクティブから退場する**ポケモン」（名前とは裏腹に、SWITCH後はベンチに行く）、`cardIdBench`/`serialBench`は「**ベンチから登場する**ポケモン」（SWITCH後はアクティブになる）を指す。フィールド名だけを見ると逆の意味に読めるため、実際に取り違えて解析していた。

**この2つの結果、`observation.current`のスナップショット（ステップ終了時点の状態）を見て「その瞬間どちらがアクティブだったか」を判定する手法は、ステップ内でSWITCH等の中間イベントが発生している場合は当てにならないと判明した。**

実例：`87211430`のstep=45、target_serial=82（フェザンディピティex）へのATTACHは、当初「アクティブはドラパルトex(121)、ベンチのフェザンディピティexへ配分＝矛盾」と判定していたが、実際にはこのATTACH（flat index 101）の**直後**（flat index 105）にSWITCHイベントがあり、そのSWITCHで初めてドラパルトexがアクティブになっていた。つまりATTACHの瞬間はフェザンディピティexの方がアクティブで、`attach_score`の専用分岐（アクティブなら22000/18000）が正しく発動していただけだった。

### 汚染範囲

上記の理由により、以下の分類は**全て信頼できない**（作り直しが必要）：
- 「25件：専用ロジックで説明済み」
- 「19件中15件：ベンチが上回る＝設計通り」
- 「19件中4件：矛盾」

65件全件を、スナップショットに頼らない方法で再判定する必要がある。

## 次回セッションでやること（Phase 1継続：正しい根本原因調査）

### Step 1: インクリメンタルなステートトラッカーを実装する

生ログのイベントを最初から順番（`src/etl/gold.py`の`build_event_timeline()`が返すフラットな時系列、ステップ境界ではなくイベント単位の順序）に再生し、以下を追跡するクラス/関数を新規実装する：
- 自分（`self_idx`）のアクティブ1体・ベンチ複数体の**serial**の割当
- 各serialの現在の**エネルギー数**
- 各serialの**種族ID**（進化で変わる）

処理すべきイベント型（`cg/api.py`の`LogType`参照、値は要再確認してから使う。前回の教訓通り**推測せず必ずコードで定義を確認する**）：
- `MOVE_CARD`（type=6）：手札/デッキから場（ACTIVE/BENCH）への配置＝新規登場
- `SWITCH`（type=8）：**上記バグ②に注意して正しい方向で反映する**
- `EVOLVE`（type=12）：`serialTarget`（進化前）の位置とエネルギーを引き継ぎ、`serial`（進化後）に置き換える
- `ATTACH`（type=11）：`serialTarget`のエネルギー数を+1
- 気絶による場からの除去（`MOVE_CARD`でACTIVE/BENCH→DISCARD）：追跡対象から外す

初期状態（セットアップ）は`data["steps"][0]`前後の`SETUP_ACTIVE_POKEMON`/`SETUP_BENCH_POKEMON`相当の初期配置、または`steps[0]`のスナップショットから組み立てる（ここは複数ターンが混在する余地がないので、スナップショットを使ってよい）。

### Step 2: 65件のベンチ向けATTACHイベント全件を、このトラッカーで再判定する

各ATTACHイベントの直前時点で：
1. その時点で本当にアクティブだったのは誰か（種族・エネルギー数）
2. `attach_score()`を種族ごとの分岐まで忠実に再現し、アクティブ候補とベンチ候補（実際に選ばれた対象）のスコアを計算する
3. アクティブの方が高スコアなのにベンチが選ばれたケースが本当に残るか集計する

このとき`bench_attacker`・`no_more_dex`もスナップショットではなくトラッカーの状態から計算する（`bench_attacker`＝ベンチにドラパルトexで2エネ以上のものがいるか、`no_more_dex`＝`自分のドラパルトex数×2 >= 相手の残りサイド`）。

### Step 3: 本当に矛盾が残るか判定する

- 矛盾ゼロ → 「ベンチへの配分は設計通り」と確定。ユーザーへ訂正報告し、このデバッグは終了（コード修正なし）
- 矛盾が残る → その事例を個別に読み、なぜ`attach_score()`の計算結果と実際の選択が食い違うのかを特定する（ATTACH_FROMの候補列挙自体に別の見落としがある可能性、あるいは真のバグの可能性）

### Step 4（矛盾が残った場合のみ）：仮説→最小修正→TDD→再提出

- 単一の仮説を立てて最小限のコード変更で検証する（本スキルのPhase 3・4に従う）
- `superpowers:test-driven-development`で失敗するテストケースを先に書く
- 修正後、`uv run pytest -q`でリポジトリ全体の回帰を確認
- `scripts/build_dragapult_submission_notebook.py`でKaggle提出用notebookを再生成
- 実装サマリーを`docs/implementations/`に保存
