## 2. ノートブックの構造

全3セル。

| セル | 種別 | 中身 |
|---|---|---|
| 0 | markdown | 環境所感が4行だけ。コードも図もなし |

### セル2（submission 生成）の処理

1. 先頭の `AGENT_SELECTION = "A"` で A / B を切り替え
2. 出力先は `/kaggle/working`（無ければ `Path.cwd()`）配下の `selected_agent_build/` を**毎回 rmtree してから再作成**
3. payload の文字列から `main.py` と `deck.csv` をそのまま書き出し
4. `py_compile.compile(main.py, doraise=True)` で構文検証（deck.csv は未検証）
5. コンペ提供の `cg` エンジンを3段フォールバックで探索してコピー。`api.py`/`utils.py` が欠けている場合のみ埋め込み複製で補完
6. **macOS 以外の環境でのみ** `main.py` を動的 import して `callable(mod.agent)` をアサート（macOS ではスキップ）
7. `submission.tar.gz` に固める

### 注意点

- payload に `main_hash` / `deck_hash`（SHA256）が入っており**実際に値は一致する**が、`hashlib` はどこにも import されておらず**実行時の照合は行われていない**。改ざん検知としては機能していない

- `DATA` の16個のチャートのうち、セル2が参照するのは `decision_mode` の**1個だけ**。残りは描画も集計もされない未使用ペイロード

## 3. エージェントA：ブリジュラスex 鋼テンポ

- **build_name**: `flex_archaludon_0018_minus1182_plus1213`（シードからボスの指令 −1 / ジャッジマン +1 した18番目の派生）
- **規模**: 1096行、52関数、クラス定義ゼロ

### ルールベースである根拠

- import は `os` / `random` / `sys` のみ。numpy・torch・sklearn・pickle いずれもゼロヒット
- **コンペAPIの先読み機能 `search_begin` / `search_step` / `search_end` を一度も呼んでいない**（＝プレイアウトなし）
- 報酬関数・価値関数・NN に相当するものなし。4桁以上のマジックナンバーが156個

意思決定の本体は `choose_options`（A:1058-1080）で、「全optionをスコア付け → 降順ソート → maxCountまで貪欲に選ぶ。負のスコアは minCount を満たしていればスキップ」というだけ。

### デッキ（60枚）

- **ポケモン13**: ジュラルドン×4 / **ブリジュラスex×4**（メタルディフェンダー 鋼鋼鋼 220） / **エースバーン×4**（特性しゅんぱつりょくで対戦準備時に2進化のままバトル場へ。フレアターボで山札から基本エネ3枚をベンチに供給） / ジーランス×1（特性きおくにもぐる）
- **グッズ/どうぐ20**: ハイパーボール4 / ポケギア3.0×4 / ジャンボアイス×4 / ポケパッド×4 / 夜のタンカ×3 / ヒーローマント×1
- **サポート12**: 探検家の先導×4 / リーリエの決心×4 / ボスの指令×3 / ジャッジマン×1
- **スタジアム4**: フルメタルラボ×4（鋼の被ダメ −30）
- **エネルギー11**: 基本鋼×11

エースバーンを進化ライン抜きで4枚積むのは事故ではなく意図的なギミック。特性で初手に必ず立て、1エネのフレアターボで鋼エネ3枚を一気に供給し、HP300/220打点のブリジュラスexを最速起動する。実測で**初撃2.66ターン**（環境最速）。

### 設計上の白眉

**スコア帯そのものを行動順序に使っている**（docstring A:33-36 に明記）。

| 帯 | 行動 |
|---|---|
| 1000〜28000 | 場の準備・プレイ・進化・エネ付け |
| 攻撃 | **与ダメージ値そのまま（最大220）** |
| 0 | ターン終了 |
| 負値 | 「打てるが今は打たない」 |

攻撃は必ず220以下なので、**優先順位のif連鎖を一切書かずに「準備を全部やってから殴る」が自動的に成立する**。我々がルカリオでスコア衝突の調整に苦労した問題を、レンジ分離で構造的に解いている。

その他、参考になった点：

- **全スコア関数が `(score, reason)` のタプルを返す**。全分岐に理由文字列が付いておりログ解析に極めて有利
- **二重の例外安全網**：option単位の try/except（A:1062-1064）＋ agent全体（A:1095-1096、`random.sample` へフォールバック）
- **進化タイミングをトラッシュ状態で制御**（A:743-762）：合金集結がトラッシュの鋼を最大2枚回収するため、トラッシュ鋼2枚以上→28000点、1枚→8000点、0枚→**−500（進化できるのにあえてしない）**
- **エネ付与の"あと一歩"優先**（A:765-798）：既存エネ数によるボーナスが `{2:12000, 1:7000, 0:4000}` と非線形。さらにHP比率補正で瀕死のポケモンには注がない
- **ボスの指令の stall モード**（A:713-737）：自分のエネが枯れて負け筋のとき、「にげるコストが重く・技のエネ要求が多く・エネが付いていない」＝最も動けない相手を引きずり出して足止めに切り替える
- **回復のオール・オア・ナッシング判定**（A:556-593）：手札のジャンボアイスを全部使っても推定被ダメージ下限に届かないなら1枚も使わない。また「回復すると Raging Hammer の KO ラインを失う」場合も使わない
- **同名カードの1枚目/2枚目の区別**（`_first_option_index`, A:305-310）：先頭indexだけ高得点にして2枚目以降を落とし、「トラッシュの鋼をちょうど2枚に制御する」を複数箇所で一貫して実現

### 実装漏れ・問題点

- **ジャッジマン(1213)に対応ロジックが皆無**。`score_play` 最終行で汎用1000点になるため、手札にある限りほぼ毎ターン打たれる。build_name が `minus1182_plus1213` なのに main.py が追随していない
- デッドコード多数（`opp_max_damage` は定義のみで未呼び出し 等）
- グローバル可変状態 `_opp_last_attack_id` は相手が攻撃しなかったターンに更新されず古い値が残る
- ディスパッチ網羅性不足：`OptionType.DISCARD` / `TOOL_CARD` / `ENERGY_CARD` / `SKILL` / `SPECIAL_CONDITION` に専用処理なし
- **このデッキ専用**。他デッキでは動かない（カードIDの直書き約30個）

作者が丸ごとパイプラインを組んで対処していたのが、まさにこの症状。

- 30候補から最良を選ぶと**12〜15ポイント分の上振れが混ざる**と実測している
- 80戦 0.7547 → 200戦 0.7085 という劣化が実際に起きている
- ライブでは 930.6 → 804.0 と **126.6ポイント**落ちた記録がある

LBスコアは対戦を重ねるほど真の実力に収束するので、「タッチした瞬間の値が上振れで、その後平均に戻っている」という説明が最もシンプルに成立する。**だとすれば改善すべきは「ピークを上げること」ではなく「上振れを実力と誤認しないこと」**であり、打ち手が変わる。

これは既存の実証「20戦の勝率/スコアでは効果判定不可能（要97戦超）」の続きに位置する。あの結論に、**「80戦スクリーニング → 別シード200戦ホールドアウト → 上振れ分を差し引く」という具体的な手順**が付いたと捉えるのが正しい。

### 示唆② ルカリオの環境評価（**要裏取り**）

作者のスナップショットではルカリオが**使用率2位（18.8%）でスコア率42.4%と最下位級**。もしこれが正しければ、「実装の詰めが甘い」のではなく「デッキ選択が環境的に逆風」という話になり、現在の改善努力の天井が決まってしまう。

ただしこれは**出典不明の他人の分類による1ヶ月前のデータ**であり、鵜呑みは危険。**我々の手元の対戦ログから自分で集計して裏を取る必要がある。**

### 示唆③ そのまま流用できる設計

1. **スコア帯のレンジ分離**（攻撃＝ダメージ値そのまま最大220、他の行動は1000点以上）。優先順位のif連鎖なしに「準備を全部やってから殴る」が成立する
2. **全スコア関数が `(score, reason)` を返す**。ログ駆動デバッグと相性が良い
3. **デッキアウト安全弁 `safe_draws`**（`deck_count - prize_count - 1`、ただし勝ち確定時は解除）
4. **同名カードの1枚目/2枚目を区別**して資源枚数を狙った値に制御する手法

### 示唆④ 逆に「やってはいけない」ことの実例

A・B **両方で「デッキに入れたカードにスコアリング側が対応していない」漏れ**が出ている（Aはジャッジマン、Bはラナのアシスト）。Bに至っては約80行が死にコード。

→ **デッキCSVに含まれる全カードIDが、スコアリング側で言及されているかを機械チェックする仕組み**を我々の側に入れる価値がある。

### 使えないもの

エージェントのコード本体。デッキ専用のハードコードの塊（マジックナンバー156個、カードID直書き約30個）で流用性がなく、品質面でも我々の実装より上ではない。

### 次の調査候補（優先度順）

1. **ルカリオ42.4%の裏取り** — 手元の対戦ログから環境のデッキ分布と各デッキのスコア率を自分で集計し、作者の数字と合うか確認する。合うならデッキそのものの見直しが議題に上がる
2. **「続かない」の実測確認** — 提出履歴のスコア推移を並べ、ピーク後の下落が平均回帰の幅に収まるかを見る。収まるなら、追うべきは実装の穴ではない
3. **評価プロトコルの整備** — 80戦→200戦の二段検証を計測スクリプトに乗せる

※ 3を先に作っても、測る対象（デッキ）が間違っていたら意味が薄いため、**1と2を先に**行うのが妥当。

## 8. 付録：ノートブックの解凍手順

エージェント本体はJSON文字列の中に押し込まれた1行（84,679文字）で、そのままでは読めない。以下のスクリプトで解凍できる（本リポジトリには解凍結果を保存していない）。

```python
import json, ast, os

NB = "notebooks/references/strong-start-baseline-agent-v10-lb-950.ipynb"
OUT = "/tmp/unpacked"          # 任意の作業ディレクトリ

nb = json.load(open(NB))
src = "".join(nb["cells"][1]["source"])   # セル1が全ペイロード

os.makedirs(f"{OUT}/agents", exist_ok=True)
vals = {}
for node in ast.parse(src).body:
    if not isinstance(node, ast.Assign):
        continue
    name = node.targets[0].id
    try:
        vals[name] = ast.literal_eval(node.value)          # 素の文字列（CG_API_PY 等）
    except Exception:
        vals[name] = json.loads(ast.literal_eval(node.value.args[0]))  # json.loads(...) 形式

for k, v in vals.items():
    if isinstance(v, str):
        open(f"{OUT}/{k}.py", "w").write(v)
    else:
        json.dump(v, open(f"{OUT}/{k}.json", "w"), ensure_ascii=False, indent=1)

# エージェント本体とデッキを個別に取り出す
for k, payload in vals["AGENT_PAYLOADS"].items():        # k は "A" / "B"
    open(f"{OUT}/agents/{k}_main.py", "w").write(payload["main_py"])
    open(f"{OUT}/agents/{k}_deck.csv", "w").write(payload["deck_csv"])
```

`DATA.json` 内のCSV文字列は `pandas.read_csv(io.StringIO(...))` で表として読める。
