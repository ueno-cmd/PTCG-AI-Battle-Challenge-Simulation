## ②ベンチへのエネルギー配分が優先される理由（ユーザー質問への回答）

20戦・123件のエネルギー装着イベントを集計した結果、**アクティブ23件・ベンチ100件（ベンチ比率81%）**。

これは「ベンチを優先している」設計ではなく、`_attach_score()`の以下のロジックの**構造的な帰結**：

```python
# main.py:82-86
if energy_count >= 2:
    if active and not can_switch and not my_asleep and not my_paralyzed:
        score += 200
    else:
        return -1   # ← アクティブが既に2エネ(攻撃可能)に達すると、以後の手張りは-1で門前払い
```

ドラパルトexの技「ファントムダイブ」は2エネルギーで撃てるため、アクティブが2エネに達した時点で
それ以上の追加投資はスコア-1になり、**以後の手張りは自動的に「まだ2エネ未満の次の控えアタッカー」
（ベンチのDreepy/Drakloak/Dragapult_ex）へ流れる**。これは「複数体に分散してダメカンを撒く」
というデッキの基本戦略（アクティブが倒れても次のアタッカーがすぐ動ける状態を維持する）に沿った
意図通りの挙動であり、バグではない。

ただし①で見た通り、その配分先の**優先順位付け自体**には（軽微だが）まだ矛盾が残っている
（クリスピンボーナスの非対称、および新規パターン1件）。

## ③「ドラパルトが倒れた後、ベンチにいたのにスボミーが出た」問題（ユーザー報告の検証）

### 再現確認

20戦を`GameStateTracker`で走査し、「アクティブが空になり新規に着地する」イベント
（`MOVE_CARD toArea=ACTIVE`、強制的な次アクティブ選択に対応）を全て抽出したところ、
**ユーザーの報告と完全に一致する事例が4件**見つかった：

| 試合/step | 倒れた側 | 新アクティブ | ベンチに残っていたDragapult_ex |
|---|---|---|---|
| 87460308 step=127 | Dragapult_ex | **Budew(スボミー)** | あり |
| 87464081 step=117 | Dragapult_ex | **Budew(スボミー)** | あり |
| 87463537 step=165 | Dragapult_ex | **Budew(スボミー)** | あり |
| 87540649 step=119 | Dragapult_ex | **Budew(スボミー)** | あり |

### 根本原因：意図的な設計（バグではない）

`main.py:687-705`の新アクティブ選択ロジック（`SelectContext.SWITCH`/`TO_ACTIVE`/`SETUP_ACTIVE_POKEMON`）：

```python
elif card.id == Dragapult_ex:
    score += 50000
elif card.id == Budew:
    if context != SelectContext.SWITCH:      # ← 強制入れ替え時(KO後など)のみ
        score += 100000                      #    Dragapult_exの2倍のスコア
    elif not bench_attacker:
        score += 30000
```

Budew（スボミー）の特性「むずむずかふん」は**「このポケモンがバトル場に出たとき、相手は次の
自分の番、手札からグッズを出せない」**という「場に出た瞬間」トリガー型の妨害効果（JP_Card_Data.csv
ID235確認済み）。強制的な入れ替え（`SelectContext.SWITCH`以外＝KOによる強制入場）の場面では、
この特性を発動させて相手のアイテム封じを取る方が、（弱点を突かれて倒された直後の危険な盤面へ）
Dragapult_exを無防備に晒すより価値が高い、という判断が明示的にコードに書かれている。
一方、**自発的な入れ替え（`SelectContext.SWITCH`、にげる等）ではBudewは+30000（bench_attacker不在時
のみ）に対しDragapult_exは常に+50000**で、通常はDragapult_ex優先に戻る。

つまり「ベンチにドラパルトexがいたのにスボミーが出た」のは、**KOされて強制的に次を選ぶ場面限定で
Budewの特性発動を優先する意図的な設計**であり、実装ミスではない。ユーザーの違和感（「なぜか」）は、
この設計意図（特性の即時発動を待避戦略より優先する）がコード上明示されているだけで見た目には
わかりにくいことに起因する。
