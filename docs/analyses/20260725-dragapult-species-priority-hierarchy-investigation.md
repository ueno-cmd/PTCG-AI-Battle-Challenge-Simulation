# ドラパルトex 種族優先度階層の再設計要否 調査（2026-07-25）

## 背景

`docs/implementations/20260725-dragapult-wasted-attach-switch-fix.md`（所感a・b修正）で、所感bの典型パターン（アクティブ=ドロンチ・0エネルギーが、ベンチのドロディーやドラパルトexに負ける）は「active/bench非対称バグ」の修正だけでは解消せず、「種族優先度階層の値そのものをどう設計すべきか」という別の設計課題が残ることが確認された。本ドキュメントは、その未解決部分を次回セッションで着手する前提で調査し、解決方針をサマリー化したものである。

**スコープ**：本調査はコード修正を行わない。設計方針の整理と提言のみ。

---

## 1. 現状の構造

`src/dragapult_agent/main.py`の`_attach_score()`、`energy_count == 0`分岐（1本目のエネルギーを装着する場面、125〜137行目）：

```python
else:  # energy_count == 0
    if pokemon.id == Dragapult_ex:
        score += 150
    elif pokemon.id == Dreepy:
        score += 100
    else:
        score += 50   # ← ドロンチ(Drakloak)はここに落ちる
    if active:
        if bench_attacker:
            score += 400
    else:
        if bench_attacker:
            score -= 200
```

ドロンチ（Drakloak、ドロメシヤ→ドロンチ→ドラパルトexの中間進化）には専用の階層が存在せず、「それ以外」の最下位枠（+50）に他の無関係な種族（マシマシラの悪エネルギー装着ケースなど）と一緒くたに扱われている。

---

## 2. 根本原因：我々のバグではなく、Kaggle公式サンプルの原文ママだった

`git show 7382bfc:src/dragapult_agent/main.py`（本プロジェクトがKaggle公式サンプルを移植した最初のコミット）を確認したところ、Dragapult_ex(150)/Dreepy(100)/else(50)という並びは**移植時点から一切変更されていない**ことが判明した。

これまで本プロジェクトが修正してきたのは以下の2点であり、階層の**値の並び順そのもの**はどちらの修正でも検証対象になっていなかった。

- 2026-07-22：`energy_count==1`分岐の「else」枠が-200点だった非対称バグを+50点に修正（ベンチ同士の比較）
- 2026-07-25（Task 3）：`energy_count==0`分岐で、アクティブ側にだけ種族ボーナスが欠落していた非対称バグを対称化

---

## 3. 決定的な矛盾：`energy_count==1`分岐との不整合

同じ関数の1つ上の分岐（`energy_count==1`、2本目のエネルギーを装着する場面、109〜124行目）を見ると、階層の考え方が逆転している。

| 分岐 | ドラパルトex(Dragapult_ex) | ドロンチ(Drakloak)＝"else" | ドロメシヤ(Dreepy) |
|---|---|---|---|
| `energy_count==1`（2本目） | +250（最優先） | +50（中位） | **-150（最下位）** |
| `energy_count==0`（1本目） | +150（最優先） | +50（＝else、最下位相当） | **+100（中位）** |

`energy_count==1`分岐は「最終進化に近いほど優先＝ドラパルトex＞ドロンチ＞ドロメシヤ」という一貫した設計思想になっている。これは合理的である：ドロメシヤはあと2回進化しないと攻撃できないため、既に1本エネルギーが付いた個体への追加投資としては最も価値が低く、逆にドロンチは「あと1進化で攻撃可能」な個体なので、ドラパルトexに次ぐ優先度を与えるべきという考え方に合致する。

一方`energy_count==0`分岐だけは「ドロメシヤを中位、ドロンチを最下位相当」という**逆順**になっている。ドロンチは中間進化であるにもかかわらず、1本目のエネルギーを取り合う場面でだけ、生まれたばかりのドロメシヤより優先度が低い。これは同一関数内で「進化段階が進んでいるほど優先」という思想を採用している箇所とそうでない箇所が混在していることを意味し、設計として一貫性を欠いている。

なお、なぜ`energy_count==0`分岐がこのような並びになっているのか（ドロメシヤを早期に育成ラインへ乗せることを意図した設計判断なのか、単に公式サンプル作成者がドロンチのケースを想定していなかっただけなのか）を示す一次資料は見つからなかった。ただし2の通り本プロジェクトの設計意図ではなく、かつ3で示した通り同一ファイル内の別分岐と矛盾するため、**意図的な設計というより見落としである可能性が高い**と判断する。

## 4. 現行デッキで実害があるのはドロンチだけ

「新規加入直後の低階層種族より、戦闘準備が近い中間進化ポケモンに適切な優先度を持たせる」という論点は一般化できる課題に見えるが、現行デッキ構成を確認したところ、対象は実質ドロンチのみである。

- ヨマワル(Duskull)→サマヨール(Dusclops)→ヨノワール(Dusknoir)系統も進化ラインだが、`_attach_score()`の98〜100行目（`elif pokemon.id == Dusknoir or pokemon.id == Dusclops: return 500`）で先に横取りされ、エネルギー種別を問わずscore=500固定となる。この分岐まで到達しないため、今回の階層問題とは無関係。
- マシマシラ(Munkidori)は悪エネルギー装着時に限り本分岐（elseの+50枠）へ到達するが、進化しない単体ポケモンであり「戦闘準備が近い中間進化」という文脈には当てはまらない。

したがって、今回の再設計は**ドロンチ専用の階層を1つ追加する局所修正**で足り、進化段階を一般化したテーブル構造（例：ステージ番号ベースの汎用計算式）まで作り込む必要はない。将来ドラパルト以外の3段階進化ラインがデッキに追加された場合に、改めて一般化を検討すれば十分である。

---

## 5. 解決方針（提案）

`energy_count==0`分岐に、`energy_count==1`分岐と同じ「進化段階が進んでいるほど優先」の考え方を適用し、ドロンチ専用の階層を新設する。

```
ドラパルトex(150) > ドロンチ(新設、ドロメシヤの100より高い値) > ドロメシヤ(100) > その他(50)
```

具体的な数値（例：120〜140の範囲）は設計フェーズで検討するが、`elif pokemon.id == Drakloak: score += X`を1行追加するだけの局所修正で実現できる。既存のelif連鎖スタイルに沿う形であり、新たな抽象化は不要。

### 影響を受ける既存テスト

`tests/test_dragapult_agent.py:812`に、現行値`(Dragapult_ex, 150), (Dreepy, 100), (Drakloak, 50)`を固定するパラメトライズテストが既に存在する。この階層を再設計する場合、当該テストの期待値更新が必須になる。

### 期待される効果

`docs/implementations/20260725-dragapult-wasted-attach-switch-fix.md`のTask 3節で確認された「実測20戦ログ中、active=Drakloak・0エネルギーの12件は1件も逆転しなかった」という制約が解消される見込みだが、実際の効果は同じ手法（`scripts/analyze_dragapult_attach_scoring.py`を用いた実測ログ再検証）での再検証が必要。

## 6. 修正アプローチの検討（2026-07-25追記）

3つの実装アプローチを比較した。

| # | アプローチ | 内容 | メリット | デメリット |
|---|---|---|---|---|
| 1 | 局所パッチ | `energy_count==0`分岐にドロンチ専用`elif`を1行追加（例：+125） | 変更最小、既存の`elif`連鎖スタイルに沿う | 優先順位が2分岐に別々の数値でハードコードされたままで、片方だけ修正されて矛盾が再発するリスクは残る |
| 2 | 優先順位テーブルの共通化 | `_SPECIES_PRIORITY_RANK`等で順位を1箇所に集約し、両分岐が参照 | 矛盾のクラス自体を構造的に解消、将来の3段階進化ライン追加にも耐える | 現状ドロンチ以外に対象がなく過剰設計になりうる。`energy_count==1`側も触るため影響範囲が広がる |
| 3 | 一貫性テストの追加 | 「ドロンチ＞ドロメシヤ」の関係をenergy_count==0と==1の両方で検証するテストを新規追加（1・2いずれとも併用可） | 値の書き換えだけでは検知できない「2分岐の思想の矛盾」の再発を防ぐ保険 | テスト設計にひと手間かかる |

### 決定事項（2026-07-25）

ユーザーは**アプローチ1＋アプローチ3**（局所パッチ＋一貫性テストの追加）で進める方針を決定した。現行デッキで実害があるのはドロンチのみであり、テーブル化（アプローチ2）による一般化は現時点では過剰設計と判断。
