## コンペ概要

- **形式**: ゲームAIシミュレーション競技（Kaggle）
- **課題**: ポケモンカードゲーム（PTCG）をプレイするAIエージェントを開発する
- **評価指標**: 対戦勝率（Win Rate）— 他エージェントとの1対1バトルで決まる
- **提出形式**: `submission.tar.gz`（`main.py` + `cg/` ライブラリ + `deck.csv` を含む）
- **ターゲット変数**: なし（強化学習・ゲームAI形式）
- **エージェントI/F**:
  - 入力: `obs_dict`（ゲーム状態の観測）
  - 出力: 選択するオプションのインデックスリスト
  - 初回呼び出し: デッキリスト（カードID 60枚分）を返す

### シミュレーションライブラリ

- `cg/api.py`: 全API定義（`Observation`, `CardData`, `Attack` 等）
- `cg/game.py`: `battle_start / battle_select / battle_finish`
- `cg/libcg.so`: Linux向けネイティブライブラリ（Kaggle環境）
- `cg/cg.dll`: Windows向けネイティブライブラリ

### 主要API

| API | 役割 |
|-----|------|
| `battle_start(deck, deck)` | バトル開始 |
| `battle_select(selected)` | 行動選択 |
| `battle_finish()` | バトル終了 |
| `search_begin / search_step / search_end` | 仮想探索（MCTS用） |
| `to_observation_class(obs_dict)` | 観測dictをクラスに変換 |

### 観測オブジェクト主要フィールド

| フィールド | 内容 |
|-----------|------|
| `obs.current.players[i]` | 各プレイヤー状態 |
| `obs.current.yourIndex` | 自分のプレイヤーインデックス |
| `obs.current.result` | バトル結果（-1=継続, 0/1=勝者, 2=引き分け） |

| `obs.select.context` | 選択コンテキスト（MAIN/ATTACH/等） |
| `ps.hand / bench / active / discard / prize` | 各ゾーンのカード |

## サンプルノートブック解析

### 1. `reinforcement-learning-and-mcts-sample-code.ipynb`（難易度: 上級）

- **アルゴリズム**: MCTS + Transformerベースのニューラルネットワーク（AlphaZero系）
- **モデル構成**:
  - エンコーダ: `EmbeddingBag` + `TransformerEncoder`（d_model=128, heads=2, 1層）
  - デコーダ: カスタム `DecoderLayer`（Multi-head Attention + FFN）1層
  - 入出力: スパースベクトル（カードID特徴量）
- **学習方式**: 自己対戦（Self-play）+ バリュー/ポリシー学習
  - 価値ロス: HuberLoss（delta=0.2）
  - ポリシーロス: HuberLoss（delta=0.1）
  - オプティマイザ: AdamW（lr=3e-4）、バッチサイズ=128
- **MCTS探索数**: わずか10回（非常に小さい）
- **スコア推移**:
  - 初期: 勝率20%（ランダムエージェント比）
  - 5イテレーション後: 勝率76%
- **使用デッキ**: メガユキノオーexデッキ（sample_deck固定）
- **弱点・改善余地**:
  - MCTS探索数が10回と極端に少ない → 探索精度が低い
  - モデルが小さい（1層のみ）
  - 対戦相手モデリングが粗い（スノーラックス/エネルギーで埋めているだけ）
  - 単一デッキでしか学習していない
  - 学習イテレーション数が少ない（5回のみ）

### 2. `a-sample-rule-based-agent-mega-abomasnow-ex-deck.ipynb`（難易度: 初級）

- **設計意図**: シンプルな入門向けデッキ。戦略的判断より「エネルギーを付けて攻撃」を繰り返す
- **弱点**: 対戦相手への適応なし。エネルギー事故に弱い。デッキ枚数管理が甘い

## 環境判定

- **判定**: 🚫 ローカル困難（Kaggle Notebook一択）
- **理由**:
  - `libcg.so` はLinux専用、`cg.dll` はWindows専用 → macOSでは実行不可
  - シミュレーションなしではエージェントのテスト自体が不可能
  - RL/MCTSには `torch.cuda.is_available()` チェックあり → GPU推奨
- **推奨環境**: Kaggle Notebook（GPU有効化 / T4以上）
- **推奨スペック**: GPU T4以上、メモリ16GB以上
- **代替案**: Dockerコンテナ（Linux環境）でローカル実行する方法はあるが複雑

## ブレーンストーミング

### 1. 有効なアプローチ候補

#### アプローチA：強化ルールベースエージェント（最短・最安定）

サンプルの中で最も高度なDragapultエージェントを拡張する方向。

**サンプルとの差別化ポイント：**
- **相手デッキ推定**：序盤に見えたポケモン・トレーナーズからベイズ的に相手デッキを推定し、行動スコアに反映
- **マルチターン攻撃計画**：「今ターンは準備、次ターンに攻撃」という2ターン先を見越した行動選択
- **コンテキスト依存プライズ管理**：残りプライズが2・3枚の局面では戦略を動的に切り替える（追い込まれた状態のリスクテイク）
- **特殊状態の積極利用**：毒・やけどをKO手段として計算に組み込む

**メリット**：実装が早い、デバッグが容易、再現性が高い  
**デメリット**：相手の創造的な戦術に対応できない

---

#### アプローチB：Search API活用のランダムMCTS（ニューラルネット不要）

サンプルのSearch APIを使い、NNなしのプレーンMCTSで探索する。

```python
# ロールアウト（ランダム）でノード価値を推定
def rollout(search_state, depth=20):
    for _ in range(depth):
        obs = search_state.observation
        if obs.current.result >= 0:
            return obs.current.result
        # ランダムに行動
        n = len(obs.select.option)
        selected = random.sample(range(n), obs.select.maxCount)
        search_state = search_step(search_state.searchId, selected)
    return 0.5  # 引き分け扱い
```

**サンプルとの差別化ポイント**：
- NNの学習コストがゼロ → 探索数を1000回に増やすことが可能
- 「対戦相手の手番シミュレーション」も組み込める（Search APIは両プレイヤーの行動を扱える）
- UCB1パラメータを調整するだけでパフォーマンス改善

**メリット**：GPU不要、学習時間不要、Search APIの特性を最大限活用  
**デメリット**：ランダムロールアウトは深い局面で精度が落ちる

---

#### アプローチC：AlphaZero型RL（長期・高精度）

サンプルのRL/MCTSを大幅に改善する。

**改善点：**
- **探索数**：10 → 200〜500回（T4 GPUなら十分速い）
- **モデルサイズ**：d_model=128, 1層 → d_model=256, encoder3層+decoder2層
- **対戦相手モデリング**：見えていないカードを確率分布でサンプリング（モンテカルロ法）
- **カリキュラム学習**：ランダム → ルールベース → 自己対戦の段階的強化
- **複数デッキ対応**：複数デッキで学習 → 汎化性能向上
- **報酬設計改善**：プライズ差に基づく中間報酬（勝ち負けだけでなく盤面優勢度を報酬に）

**サンプルの弱点（具体的）：**
- `SEARCH_COUNT = 10` は致命的に少ない（AlphaGoは1600回）
- 対戦相手の未知デッキを単一カード（スノーラックス）で代表するのは粗すぎる
- `LAMBDA = 0.9` のTD学習のみで、GAE（Generalized Advantage Estimation）を使っていない

**メリット**：理論的な上限が最も高い  
**デメリット**：学習に多くのKaggle GPU時間が必要

---

#### アプローチD：ハイブリッド（推奨）

ルールベース + Search APIロールアウトMCTS の組み合わせ。

```
[ルールベース層] → 確実に正しい行動（進化・エネルギー付け等）を先に処理
      ↓
[MCTS層] → 複雑な判断（どこに攻撃するか、どのカードを使うか）をSearch APIで探索
      ↓
[フォールバック] → 探索失敗時はヒューリスティックで処理
```

**メリット**：安定した動作 + 深い局面での最適化  
**デメリット**：実装の複雑さが増す

### 2. サンプルノートブックの弱点分析

#### RL/MCTSノートブック
| 弱点 | 影響 | 改善策 |
|------|------|--------|
| MCTS探索10回 | 探索木が浅く精度低 | 200〜500回に増加 |
| モデル1層のみ | 複雑な盤面を表現できない | 3〜6層に増加 |
| 対戦相手を単一カードで代表 | 相手の手を全く読めない | カード確率分布でサンプリング |
| 単一デッキのみで学習 | 特定デッキに過学習 | 複数デッキで学習 |
| 5イテレーションのみ | 収束が不十分（76%止まり） | 50〜100イテレーション |
| ランダムエージェント相手のみ | 弱い相手に最適化 | カリキュラム学習導入 |

#### ルールベースエージェント共通
| 弱点 | 影響 | 改善策 |
|------|------|--------|
| 相手適応なし | 特定のデッキに弱い | 相手デッキ推定を追加 |
| 各ターン独立評価 | 2ターン先の準備ができない | 攻撃プランシステムを全デッキに追加 |
| コイン裏表を考慮しない | 確率的効果で損をする | 期待値で評価 |
| 特殊状態への対処が弱い | 毒・やけどで余計に削られる | 特殊状態回復コストを評価に組み込む |

### 3. 落とし穴・注意点

#### プライズ管理の罠
- **exポケモンのKO = 2プライズ献上**：exポケモンをバトル場に出すタイミングが最重要
- **残り2プライズの局面**：相手が1KOでゲームを決める → 防御的行動にシフトが必要
- **メガexポケモン（3プライズ）**：サンプルには含まれていないが他プレイヤーが使う可能性大

#### Search APIの落とし穴
- 探索中は実際のバトル状態は変わらない（純粋なシミュレーション）
- `search_end()` の呼び忘れでメモリリーク
- 探索コスト（時間）が多すぎるとタイムアウトの可能性 → 探索数の上限管理が必要

#### デッキ選択の罠（最重要）
- **「最強デッキ≠最高勝率」**：他参加者のデッキと相性が決め手
- **格闘弱点**：多くのカラー/ノーマルタイプが格闘弱点 → 格闘デッキが有利
- **非exアタッカー優位性**：イイネイヌ（1プライズ）のように非exアタッカーは相手に与えるプライズが少ない
- **先行2ターン目攻撃**：先行（ファーストプレイヤー）は1ターン目に攻撃できない → テンポが遅い

#### ローカル実行の罠
- macOSでは `libcg.so` が動かない → 実装のテストはKaggle Notebook上で行う必要あり
- ただし、ロジックの設計・コード作成はローカルで可能

#### 評価の罠
- サンプルのRL実装の「勝率76%」はランダムエージェント相手 → 実際の対戦では遥かに低い可能性
- リーダーボードは他の参加者エージェントとのバトルで決まる → 公開情報から相手デッキを予測する重要性

### 4. 差別化ポイントと優先行動

#### フェーズ1（即効性・最優先）
1. **デッキ選択の最適化**
   - `EN_Card_Data.csv` を分析し、強力なカードの組み合わせを特定
   - 格闘・水・雷デッキの弱点/耐性を確認してメタゲームを読む
   - 非exアタッカー中心 + 速攻型デッキを検討

2. **サンプルの最高難度エージェント（Dragapult）を自分のデッキに適合させる**
   - デッキを変えてもロジックの骨格は流用可能
   - Search APIのテストベッドとして使用

#### フェーズ2（中期改善）
3. **Search API活用のランダムMCTS実装**
   - NNなしで探索数を100〜200に増やすだけで大きく改善
   - まずランダムロールアウトで上限を計測

4. **相手デッキ推定システム**
   - 序盤に見えたカードからどのデッキか推定（ベイズ更新 or カード共起）
   - 推定デッキに応じてスコアリングを調整

#### フェーズ3（後半戦の仕込み）
5. **NN強化（時間があれば）**
   - d_model=256, encoder3層に拡大
   - 複数デッキで自己対戦学習
   - アンサンブル（ルールベース + NN出力の加重平均）

6. **デッキの最終調整**
   - 学習結果を踏まえた最終デッキ構成
   - カード枚数最適化（枚数によって戦略が変わる）

---

### 5. 勝率向上のための重要な洞察

#### 「Search API」はこのコンペ最大の武器
サンプルノートブック通り、Search APIは**実際の対戦状態を変えずに仮想的に先の展開をシミュレーション**できる。これはほとんどのゲームAIコンペでは提供されない強力なツール。活用次第で：
- 攻撃の実際のダメージを事前計算（不確実性排除）
- 複数ターン先の盤面を事前評価
- 相手のバリエーションに対してミニマックス探索も可能

#### 「勝ち確局面の早期認識」
プライズ枚数の差から「あと何KOで勝ち」を常に計算し、勝ち確局面では最速KOルートを選ぶ。逆に負け確局面では時間を稼ぎ逆転のチャンスを待つ。これはDragapultのサンプルコードに一部実装されているが、全デッキに適用すべき概念。
